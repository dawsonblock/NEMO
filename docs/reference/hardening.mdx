The hardened development line adds runtime controls and qualification evidence
without treating scaffolding as enforcement. Run
`scripts/qualification/run.sh` inside the pinned `.devcontainer` to create the
machine-readable reports in `qualification/`.

The subscriber dispatcher uses a bounded queue with reserved capacity for
scope, lifecycle, security, authority, and audit events. Lower-priority events
are dropped with an explicit warning when that reserve is needed; high-priority
events apply backpressure. Queue counters are available as
`relay_event_queue_depth`, `relay_event_queue_capacity`,
`relay_event_queue_high_watermark`, `relay_events_enqueued_total`,
`relay_events_dropped_total`, and `relay_events_backpressured_total` in the
Rust, Python, and Node APIs. `flush_subscribers()` remains the graceful drain
barrier for queued callbacks and terminal publications.

`plugins validate` reports `policy_mode = effective` by default and applies
secure activation defaults (`required` startup and `signature_required`
attestation) before evaluating the manifest. Pass `--declared` only when you
need to inspect configuration without those runtime defaults. `--effective`
remains accepted for script compatibility.

All asynchronous runtime queues are required to have an explicit capacity and
overflow policy. The current capacities, producer/consumer ownership, and
shutdown behavior are tracked in [the queue inventory](../queue-inventory.md).
The corresponding mutable registries and per-runtime isolation rules are
tracked in [the runtime global-state inventory](../runtime-global-state.md).
Telemetry may be dropped with metrics; lifecycle, security, and execution
traffic uses backpressure or an explicit rejection path. Nested subscriber
publications are capped as well, so a callback cannot bypass the dispatcher
bound by emitting an unbounded event storm.

Response-cache identity is explicit and fail-closed. The default session
partition includes the root scope and trusted policy epoch; principal and
tenant modes require an immutable `RuntimeIdentity` installed by an
authentication boundary. Ordinary scope metadata is ignored for cache
partitioning. Buffered LLM and tool misses use process-local single-flight
coalescing. Cache writes expose `flush_cache_writes()` and
`wait_for_cache_idle()` for deterministic shutdown.

Qualification is provenance-bound. The harness writes `source-manifest.json`,
`source-tree.sha256`, `environment-lock.json`, and lockfile digests before it
runs checks. Missing prerequisites are recorded as `NOT_RUN` with a reason;
they do not become a test failure or an implicit pass. A report with any
`NOT_RUN` or `INCONCLUSIVE` check remains `DEV`/`INCONCLUSIVE` and is not a
release certificate.

The authority, ledger, and executor crates provide experimental kernel
contracts and adapter boundaries. Production authority enforcement, durable
action/receipt storage, isolation enforcement, and outbound DLP remain
external and unconfigured in this development release.

## Experimental effect-state contracts

The opt-in kernel contracts use one consequential-effect vocabulary:
`PROPOSED`, `AUTHORIZED`, `PREPARED`, `DISPATCHING`, `COMMITTED`, `FAILED`,
`UNKNOWN`, `RECONCILING`, and `CANCELLED`. An external `ActionStore` claims an
idempotency key in `PROPOSED`; a verified authority grant is bound atomically
with `PROPOSED → AUTHORIZED`, then the kernel advances the action to
`PREPARED`. Restarted `AUTHORIZED` and `PREPARED` actions can obtain a fresh
grant for the same immutable action before continuing; raw arguments are not
reconstructed from the kernel's action record.

`COMMITTED` is only written after an external execution backend returns a
receipt that binds the action, idempotency key, runtime identity and
environment/session binding digest, capability generation, admission, policy,
route, arguments, and grant. If dispatch may
have crossed the provider boundary, or if durable receipt/state persistence
cannot prove a terminal result, the kernel records `UNKNOWN` and returns a
typed reconciliation-required outcome.

`COMMITTED` and reconciliation-derived `FAILED` both require authoritative
persisted evidence. An `ActionStatus` distinguishes its last observed durable
state from an intended state that could not be persisted, and exposes a
state-specific next action such as retrying authority, resuming pre-dispatch
work, recovering, reconciling, or returning a receipt. It never presents an
unpersisted intended state as durable fact.

`MUTATION` and `CRITICAL` invocations require a stable caller `request_id`.
The kernel scopes that retry identity to the authenticated tenant and
principal, claims one durable logical action, and returns that real action ID
on every pending, unknown, or recovery-required outcome. Retrying the same
request therefore resumes or observes the original action rather than
silently creating another dispatch. Dispatch and reconciliation transitions
require a fenced external `ActionLease` containing an owner, generation, and
expiry. A recovery worker can take over only after that lease expires, so it
cannot turn a live dispatch into spurious ambiguity. A stale `DISPATCHING`
action can be recovered only from a fully bound persisted receipt; otherwise
it becomes `UNKNOWN` and must be reconciled. A stale `RECONCILING` action
returns to `UNKNOWN` under the same fencing rule. The action record retains
the highest issued lease generation even after a lease is released, so a later
owner cannot reuse a previous fencing token. While another lease is live, the
kernel returns `WAIT_FOR_OWNER` rather than suggesting recovery or redispatch.

### Lease, receipt, and recovery contract

The experimental `ActionStore` contract is the authority for lease time. A
caller can request a bounded lease duration, but cannot supply `now`, an
expiry, or any other authoritative timestamp. The store obtains time from its
own clock and applies `LeaseConfiguration` (default duration, maximum
duration, and whether renewal is enabled). A renewal is compare-and-swap-like:
only the exact current owner and fencing generation may renew a still-valid
lease. An expired or replaced lease returns `LEASE_LOST`; it never gives a
previous worker renewed authority.

Before dispatch or provider reconciliation, the kernel requests a lease long
enough to cover the bounded backend deadline plus a safety margin. The store
may reject that request when its maximum duration cannot cover the work. The
kernel renews the exact fenced lease immediately before the provider call and
passes the same deadline to the backend or reconciliation provider. Backends
must honor that kernel-owned deadline; a synchronous backend that cannot honor
it is not a valid implementation of this contract. The runtime does not
promise a background renewal daemon: long-running renewal policy remains
owned by the external Effect Fabric implementation.

Lease operations return typed outcomes rather than boolean success:
`ACQUIRED`, `EXPIRED_RECLAIMED`, `HELD_BY_OTHER`, `RENEWED`, and
`LEASE_LOST`. A `PREPARED` action with a live lease is not available for retry,
cancellation, or a second executor. Lease expiry grants permission to examine
evidence and recover; it is not evidence that a previous dispatch did nothing.

`ReceiptStore::finalize` is append-only and accepts only structurally complete
`COMMITTED` or `FAILED` receipts with a non-empty evidence digest. Receipt identity is canonical: it
includes the action/security/provider evidence bindings but excludes a local
receipt ID and collection timestamps, so a recovery worker can replay the
same provider evidence idempotently. A materially different finalization for
the same action returns `FINALIZATION_CONFLICT`, records one canonical
immutable conflict history entry, and must not overwrite the first receipt.
Repeating that exact contradiction returns `CONFLICT_ALREADY_RECORDED` rather
than multiplying forensic records. This makes contradictory terminal evidence
visible to the caller instead of silently rewriting action history. The
generic state-transition API cannot write `COMMITTED` or externally meaningful
`FAILED`; `ActionStore::finalize_from_evidence` must verify the current state,
fenced lease, immutable action binding, and evidence-authorized terminal
transition in one operation. Lifecycle legality and method legality are
separate contracts: `authorize_action` alone may write
`PROPOSED → AUTHORIZED`; generic transition alone may write
`AUTHORIZED → PREPARED` or pre-dispatch cancellation; and only a live fenced
lease may write dispatch, reconciliation, or uncertainty transitions. A
missing, empty, or whitespace-only grant digest blocks authorization,
preparation, and terminal-evidence construction.

New `PROPOSED` claims must not carry a grant digest or approval reference;
only `authorize_action` may attach them. An action-ID collision is a typed
conflict and must never overwrite an existing durable action.

For a real durable adapter, the kernel consumes one `DurableEffectStore` for
the entire consequential lifecycle. Terminal receipt persistence and the
fenced action transition are one `EffectStore::finalize_terminal_receipt`
operation. The same contract provides an `EvidenceSnapshot` containing the
action, primary receipt, retained conflicts, and a monotonic evidence revision.
Writable action or receipt sub-stores are not exposed by the aggregate reference
implementation, so terminal writes cannot bypass the transactional boundary.

Post-terminal evidence uses `observe_terminal_evidence`, not terminal
finalization. Exact evidence is idempotent. Contradictory evidence appends one
deduplicated conflict and advances the evidence revision without replacing the
primary receipt or rewriting the terminal action state. Observation cannot
establish a missing primary receipt; that remains exclusive to fenced
finalization.

Reconciliation uses `begin_reconciliation` to validate its lease, inspect one
consistent evidence view, and transition `UNKNOWN → RECONCILING` atomically.
Terminal or inconclusive completion must present the revision returned by that
operation. If evidence changed while the provider was queried, completion fails
closed and the worker reloads evidence before deciding again. Provider calls
occur between store transactions; implementations must not hold a database
transaction open across an external request.

`InMemoryEffectStore` makes these ordering rules executable for tests only;
its deterministic fault injector covers validation, staged receipt insertion,
action terminalization, revision increment, and commit boundaries. Every
injected failure must leave the complete pre-transaction snapshot, and the
one-shot retry must be able to commit the complete terminal snapshot.

The opt-in `unstable-postgres` feature provides `PostgresEffectStore` with a
bounded connection pool and an idempotent migration for actions, primary
receipts, and deduplicated conflicts. It locks the action row before lifecycle
writes, uses `clock_timestamp()` for lease decisions, reads evidence under one
repeatable-read snapshot, and commits terminal receipt, action state, lease
release, and evidence revision in one transaction. Run the same generic suite
against an isolated disposable schema with:

```bash
NEMO_RELAY_TEST_POSTGRES_URL='host=/tmp dbname=postgres user=postgres' \
  just test-postgres-effect-store
```

The adapter remains experimental and disabled by default. Passing this suite
alone does not establish restart, crash-matrix, load, real-provider, or release
qualification.

Recovery is evidence-aware. It checks persisted conflicts and terminal
evidence before calling a provider reconciler, then distinguishes a live
owner, fully bound terminal state, missing terminal evidence after lease
expiry, and contradictory evidence. A primary receipt paired with a
non-terminal action is an integrity violation rather than a state-repair path,
because conforming stores make those writes atomic. Missing evidence remains
`UNKNOWN` (or becomes recoverable under the external effect policy); it is
never translated into `FAILED` merely because a worker disappeared. The
in-memory stores and deterministic clocks are reference implementations for
these contract tests only. They do not enable production durability.

### Contract conformance testkit

The `unstable-hardening-testkit` feature exposes backend-independent store
conformance runners. An adapter supplies a fresh aggregate effect store plus a
controller for its store-owned test clock, then runs the same lifecycle, lease,
idempotency, immutable-receipt, conflict-history, stale-worker, and
reconciliation-revision cases as the in-memory reference store. The mutation
matrix changes each bound action/evidence field independently and asserts that
rejected input cannot alter durable state or evidence history. Receipt replay
and conflict tests independently mutate provider request identity, terminal
state, and evidence digest. This suite is a contract gate; it does not by itself
qualify production durability.

An action's runtime binding digest canonically covers its stable runtime or
deployment identity, environment, and session provenance. Deployments using
durable actions must keep `runtime_id` stable across a process restart; it is
not a per-process random identifier. Contradictory receipt evidence produces
`REPAIR_EVIDENCE`, not ordinary reconciliation guidance. It requires an
operator or the external evidence owner to resolve the integrity conflict.

Retry policy is deliberately conservative: `FAILED` after confirmed
pre-dispatch failure may be evaluated for a new attempt by the external effect
system; `UNKNOWN` must never be automatically re-dispatched. An external
reconciliation provider must resolve it with evidence to `COMMITTED`,
`FAILED`, or remain `UNKNOWN`. Explicit authority denial cancels the claimed
action; authority modification cancels it and returns structured constraints
for a new invocation with a new identity. Effect Fabric owns dispatch and
provider reconciliation; deployments may supply the opt-in PostgreSQL adapter
or another conforming durable store for actions, leases, and evidence.

The built-in `nemo_guardrails` component remains available for compatibility and
is formally deprecated. New deployments should use current guardrail and
intercept APIs; removal is deferred to the next breaking release with a
migration notice.
